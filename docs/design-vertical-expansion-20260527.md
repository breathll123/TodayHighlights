## Problem Statement

今日看点目前是一个单垂类（股票）的实时信息看板。用户需要的是一个多主题聚合平台——股票、AI、足球只是第一批垂直领域。当前架构（topics 表、多路由 page_blocks、source adapter）已经支持多垂类，但前端导航栏硬编码了路由，topic 系统未激活。

## What Makes This Cool

一个看板聚合三个完全不相关的信息世界——股票涨跌、AI 论文、足球比分——在同一套 UI 下用统一的时间线、卡片、表格呈现。从"股票工具"变成"信息中枢"。

## Constraints

- 后端 adapter 架构不动（`app/sources/` + `get_adapter(site)` 分派）
- 数据采集→存储→展示的三层架构不动
- 前端 shadcn/ui + Tailwind + framer-motion 技术栈不动
- DB topics 表和 page_blocks 的多路由机制已就绪，直接激活

## Premises

1. 用户获取信息的最大痛点不是"找不到"，而是"太分散"——不同垂类散落在不同平台
2. 每个数据源只在某一个垂类里最强，不应被绑死在单一平台上
3. 对非职业用户来说，"看懂现在发生什么"比"精确数据"更重要

以上三条在 office hours 中已确认。

## 股票垂类现状（已落地基线）

新垂类的 adapter / source_type / 展示样式应参照股票垂类已跑通的形态。当前股票垂类（topic slug `stocks`）接入了三个平台，共 15 个 source_type，全部走"采集→`raw_items`/直连→看板"管道。

### 三个平台的 adapter

| 平台 | adapter (`app/sources/`) | site | 认证 | 已接数据 |
|------|--------------------------|------|------|----------|
| 雪球 | `XueqiuAdapter` | `xueqiu` | 手动 Cookie（后台填入） | 推荐 Feed、热门话题、热股榜（沪深/港/美）、活跃股筛选 |
| 东方财富 | `EastmoneyAdapter` | `eastmoney` | 行情类免认证；龙虎榜走 Playwright Cookie | 概念/行业板块、主力资金、指数、龙虎榜、A股公告 |
| 同花顺 | `TonghuashunAdapter` | `tonghuashun` | 免认证（移动端 UA） | 财经快讯 |

> adapter 协议见 `app/sources/base.py`（`SourceAdapter.fetch(entry_url, cookie) -> list[RawItemDraft]`），注册在 `app/sources/__init__.py` 的 `ADAPTER_REGISTRY`。各平台的 API 地址、参数、字段映射见 [sources-api-reference.md](sources-api-reference.md)。

### source_type → 数据来源映射

看板方块的 `source_type` 决定数据如何解析（`services/blocks.py` 的 `resolve_block_data`）。两种取数路径：**采集落库**（看板读 `raw_items`）或**展示期直连**（`services/adapters/` 实时拉取 + 30s TTL 缓存）。

|-------------|------|----------|----------|
| `topic` | 本地 | DB `highlights` | 卡片 |

| `eastmoney_sectors` | 东方财富 | 直连 | 列表 |
| `eastmoney_industry` | 东方财富 | 直连（N+1 取领涨股） | 列表 |
| `eastmoney_indices` | 东方财富（新浪 API） | 直连 | 列表 |
| `eastmoney_capital_flow` | 东方财富 | 直连 | 列表 |
| `eastmoney_announcements` | 东方财富 | 直连 | 列表 |

| `tonghuashun_news` | 同花顺 | 采集落库（读 `raw_items`） | 时间线 |

### 给新垂类的启示

- **展示形态已被三种样式覆盖**：实时榜单→列表（动态列 + 数值字段排序）、深度内容→卡片、流式资讯→时间线。AI 垂类的论文/HN 头条天然适配卡片 + 时间线，无需新 display_style。
- **两条取数路径按数据时效选择**：高频变化（行情、榜单）适合展示期直连 + TTL 缓存；低频或需要 AI 摘要的（资讯、公告）适合采集落库。新垂类的论文/比分若需历史留存或 AI 摘要，走采集落库。
- **动态列已通用化**：`source_config.display_fields` + `lib/field-defs.ts` 让前端零改动支持新字段，新 source_type 只需在 `field-defs.ts` 补一行 `DEFAULT_FIELDS`。

## Approaches Considered

### Approach A: 先加数据源，后改 UI

给 AI 和足球各加 1-2 个爬虫，内容混在现有看板里展示，UI 暂时不动。

- Effort: S
- Risk: Low
- Pros: 数据先流进来，最快的验证路径
- Cons: UX 混乱——足球比分和股票涨幅混在一起，新垂类没有独立入口

### Approach B: 通用数据接入框架

做一个通用的 RSS/API 适配器，让用户自己在后台配置 URL 就能接入任何内容源。

- Effort: L
- Risk: High
- Pros: 以后加新垂类零代码
- Cons: 过度抽象，两个垂类就做通用框架是 premature。不同源的数据结构差异太大（比分 vs 论文 vs 快讯），通用适配器要么太薄没用，要么太厚维护成本高

### Approach C: 激活 Topic 系统（推荐）

把现有的 topics 表和多路由 page_blocks 机制用起来。导航栏动态化，每个 topic 有独立的看板布局和数据源配置。

- Effort: M
- Risk: Low
- Pros: 最小的代码改动，最大的 UX 提升。topic 系统、多路由、source 关联已就绪
- Cons: 每个新垂类仍需单独调研和写 adapter

## Recommended Approach

Approach C — 激活 Topic 系统。

### 实施步骤

#### Phase 1: Topic 系统激活（前端）

**PublicNavbar 动态化**
- 从 `GET /api/public/topics` 读取启用的 topic 列表
- 动态渲染导航项，替代当前硬编码的 `摘要` 和 `股票`
- 路由规则：`/topics/{slug}` 对应每个 topic 的公开看板页

**AdminLayoutPage 改造**
- 页面 Tab 从 topics 表动态加载，替代硬编码的 `pages` 数组
- 当前只显示有 draft 方块的 topic，或显示所有启用的 topic
- 编辑/预览/发布操作仍按 page_route 隔离

**新增 Topic 管理能力**
- 现有的 topics CRUD（`/api/admin/topics`）已经完整
- 前端 AdminTopicsPage 只需要确认能正常创建/编辑/启用 topic
- 新建 topic 后自动出现在导航栏和后台页面 Tab 中

#### Phase 2: AI 垂类数据源

**候选数据源：**

| 数据源 | 内容 | API 类型 | 难度 |
|--------|------|----------|------|
| Hacker News | 技术/创业头条 | Firebase REST API，公开 JSON | 低 |
| arXiv CS.AI | AI 论文 | OAI-PMH / RSS，公开 | 低 |
| Papers With Code | 论文 + 代码 + 排行榜 | 有非官方 JSON endpoint | 中 |
| Reddit r/MachineLearning | AI 讨论热帖 | Reddit JSON API，公开 | 低 |

**推荐首批：** Hacker News（覆盖面广、API 简单）+ arXiv CS.AI（AI 垂类核心内容）

**实现路径：**
1. 调研 HN 和 arXiv 的 API 格式，确认字段映射
2. 新建 `app/sources/hackernews.py` 和 `app/sources/arxiv.py`，实现 `SourceAdapter` 协议
3. 在 `__init__.py` 的 `ADAPTER_REGISTRY` 注册 `"hackernews"` 和 `"arxiv"`
4. 在 topics 表创建 `AI` topic（slug: `ai`）
5. 在 sources 表创建对应 source 行，关联到 AI topic
6. 前端无需代码改动——导航栏动态化后自动出现 AI tab

#### Phase 3: 足球垂类数据源

**候选数据源：**

| 数据源 | 内容 | API 类型 | 难度 |
|--------|------|----------|------|
| 懂球帝 (dongqiudi.com) | 新闻、赛程、社区 | 需逆向 APP API | 高 |
| 直播吧 (zhibo8.cc) | 新闻聚合 | HTML 抓取 | 中 |
| football-data.org | 欧洲联赛比分/赛程 | REST API，免费 tier | 低 |
| API-Football (v3) | 全球联赛数据 | REST API，免费 tier | 低 |

**推荐首批：** football-data.org（正规 API、免费用、覆盖欧洲五大联赛）

**注意：** 足球垂类的数据形态和股票完全不同（赛程表、积分榜、比分直播），可能需要扩展 `RawItem` 的 `metrics_json` 结构，或者新增专门的 display_style。这个垂类应该先调研数据形态再动手。

### 架构影响

```
导航栏（动态）
  /topics/stocks   → 雪球 + 东方财富 + 同花顺
  /topics/ai       → HN + arXiv + ...
  /topics/football → football-data.org + 懂球帝 + ...

管理后台
  页面切换 → 按 topic 动态生成 Tab
  每个 topic 独立的 draft/published 方块
  数据源管理 → 按 topic 过滤
```

**不改动的部分：**
- adapter 分派机制（`get_adapter(site)`）
- 采集管道（`jobs.py` → `save_raw_items` → Highlights）
- 方块配置 UI（BlockConfigPanel / BlockEditor）
- 公开页面渲染（GridRenderer / BlockCard / NewsTimeline）

**需要新增的文件：**
- `app/sources/hackernews.py`
- `app/sources/arxiv.py`
- 或 `app/sources/football.py`（足球源）
- 相应的 migration 插入 source 和 topic 行

**需要修改的文件：**
- `frontend/src/components/layout/PublicNavbar.tsx` — 动态化
- `frontend/src/pages/AdminLayoutPage.tsx` — 动态化页面 Tab
- `frontend/src/App.tsx` — 或新增动态 topic 路由（如果不再硬编码 `/topics/stocks`）

## Open Questions

1. AI 垂类的展示形态是什么？论文标题+摘要+链接，用卡片还是时间线？还是两者都支持让用户选？
2. 足球比分/赛程的数据结构（比赛时间、主客队、比分、联赛）是否需要新的 display_style？
3. 每个新垂类是否需要独立的 AI 摘要（enable_highlight）？还是只是聚合展示？
4. 导航栏动态化后，`/` 首页应该显示什么——是否需要一个"全部 topic 摘要"的聚合页？

## Success Criteria

- 导航栏从 topics 表动态生成，不再硬编码
- 管理后台可切换 topic 编辑不同页面的看板
- 至少一个 AI 数据源上线，可在看板中展示
- 至少一个足球数据源完成调研（可延后实现）
